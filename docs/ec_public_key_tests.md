# EC Public Key tests


## Motivation

An EC public key is a point $Q = dG$ on a named curve. Here $d$ is the private
key, $G$ is the generator of the curve and $n$ is the order of $G$. Paranoid
sees only the curve and the point, never $d$. The EC key checks look for
weaknesses that can still be seen from the public side:

*   The key or its curve is malformed or unsupported.
*   The curve is so small that discrete logarithms on it are not hard enough.
*   The key generator produced private keys with so little entropy that $d$
    can be computed from $Q$ alone, or from the private key of a related key.

Passing every check does not prove that a key is strong. It only means the key
has none of the weaknesses described below.

## Running the checks

`paranoid.CheckAllEC` runs the active checks on a list of `paranoid_pb2.ECKey`
messages, in the order listed under [Checks](#checks). Each key needs
`ec_info.curve_type` and the affine coordinates `ec_info.x` and `ec_info.y` as
unsigned big-endian bytes. An unset coordinate is read as 0 and raises no
error. The call returns `True` if any check flagged any key.

Each check that runs on a key records an entry in `test_info.test_results` with
the check name, the result and the severity. If the key already has an entry
for that check, for example from an earlier run, the entry is updated instead:
the results are OR-ed and the higher severity is kept. A flagged key gets
`test_info.weak = True`. Neither a `True` result nor `weak` is ever reset to
`False`. Some checks also attach details to `test_info.attached_info`, as
described under each check.

The same checks also run on the issuer keys of ECDSA signatures, through
[CheckIssuerKey](ecdsa_signature_tests.md#checkissuerkey).

The EC checks use no bundled data files. Every result is computed from the
curves and points of the keys passed in.

Check                     | Input  | Severity          | A key fails when
------------------------- | ------ | ----------------- | ----------------
CheckValidECKey           | single | SEVERITY_MEDIUM   | its curve is not implemented or its point is not a valid public key
CheckWeakCurve            | single | SEVERITY_MEDIUM   | its curve order is shorter than 224 bits
CheckWeakECPrivateKey     | single | SEVERITY_CRITICAL | the search for low-entropy private keys described below finds its private key
CheckECKeySmallDifference | batch  | SEVERITY_HIGH     | its private key differs by less than $2^{24}$ from that of another key on the same curve in the same call (the bound can be larger, see below)

## Supported curves

`ec_util.CURVE_FACTORY` implements nine curves over prime fields. All of them
have cofactor 1. The last column gives the number $f$ of multipliers that
CheckWeakECPrivateKey searches on each curve.

Curve           | Order length (bits) | Multipliers $f$
--------------- | ------------------- | ---------------
secp192r1       | 192                 | 26
secp224r1       | 224                 | 31
secp256r1       | 256                 | 36
secp256k1       | 256                 | 36
brainpoolP256r1 | 256                 | 36
secp384r1       | 384                 | 56
brainpoolP384r1 | 384                 | 56
brainpoolP512r1 | 512                 | 76
secp521r1       | 521                 | 77

`CurveType` also has ten curves over binary fields: sect163k1, sect233k1,
sect283k1, sect409k1, sect571k1, sect163r2, sect233r1, sect283r1, sect409r1
and sect571r1. They are listed in `CURVE_FACTORY` but have no implementation.
The code marks them as curves to avoid, citing Semaev's discrete logarithm
algorithm for elliptic curves over binary fields [[Semaev]]. The complexity
estimate in that paper rests on a heuristic analysis.

CheckValidECKey reports a key on one of these curves, or on `CURVE_UNKNOWN`, as
a key on an unknown curve. For a binary-field curve this says nothing about the
point: it only means that Paranoid cannot test the key. The other three checks
skip such a key and record no result for it.

## Checks

### CheckValidECKey

Checks whether each key is a valid public key on a known curve. An invalid EC
key might mean that whoever created it is attempting an invalid curve attack.
If invalid keys turn up, investigate the keys and the application that uses
them.

A key fails in two cases: its curve has no implementation in `CURVE_FACTORY`,
or `EcCurve.IsValidPublicKey` rejects its point. That method requires all of
the following:

1.  The point is on the curve.
2.  The point is not the point at infinity.
3.  The point is in the subgroup generated by $G$. This is tested only when the
    cofactor $h$ is larger than 1.
4.  Both affine coordinates are in the range $[0, p - 1]$, where $p$ is the
    field prime.

These are the checks of the public key validation primitive in SEC 1, section
3.2.2.1 [[SEC1]], which notes that requirement 3 follows from the others when
$h = 1$. Every supported curve has $h = 1$, so requirement 3 is never tested.
For an `ECKey`, requirement 2 never fails either: an `ECKey` cannot encode the
point at infinity, and unset coordinates are read as $(0, 0)$, which fails
requirement 1 on every supported curve. Requirement 4 rejects an unreduced
coordinate such as $x + p$. Such a coordinate still satisfies the curve
equation modulo $p$, so it passes requirement 1.

A failure does not stop the other checks, and a malformed point does not abort
the run. A key on a supported curve with an invalid point still goes through
CheckWeakCurve, CheckWeakECPrivateKey and CheckECKeySmallDifference.
CheckWeakECPrivateKey first reduces both coordinates modulo $p$ and searches
only points that are then valid. A point that is not on the curve has no
private key and passes that check; this includes a point with $y = 0$, such as
a key whose coordinates are both unset. An unreduced encoding of a valid point,
such as $x + p$, is searched as the point it encodes, so a weak private key is
still found. The results of CheckECKeySmallDifference for an invalid key are not
reliable, so treat a key that fails CheckValidECKey as an invalid key first.

### CheckWeakCurve

Checks whether a key uses a weak curve: one on which discrete logarithms take
significantly less than $2^{112}$ operations. Computing the private key from the
public key is a discrete logarithm, so on a weak curve it costs less than that.

The check fails a curve whose order $n$ is shorter than 224 bits. It uses only
the curve type, not the point. This matches NIST SP 800-57 Part 1 Rev. 5,
Table 2 [[SP800-57]], which gives a security strength of 112 bits to EC keys
whose order is 224 to 255 bits long, and at most 80 bits to orders of 160 to
223 bits. The check compares bit lengths, so a 224-bit curve whose order is
slightly smaller than $2^{224}$ still passes. Of the supported curves, only
secp192r1 fails.

### CheckWeakECPrivateKey

Checks whether a private key has one of these low-entropy forms:

1.  Only the 32 least significant bits are set.
2.  Only the 32 most significant bits are set.
3.  All 32-bit words of the private key are the same.

The check is motivated by research that scanned Ethereum (secp256k1) private
keys whose set bits all lie in one of the eight 32-bit words, with all other
bits zero [[ethercombing]]. It found 464 such keys with transactions in the
lowest word, 264 in the highest word and 4 in the six words between. Form (3)
goes beyond what that research scanned. Each form leaves fewer than $2^{32}$
candidates for $d$. That is few enough for the check to compute the private key
itself, and anyone else can do the same.

Solving discrete logarithms for the 32 least significant bits is enough to
cover all three forms. Suppose $d = i \cdot m \bmod n$, with $0 < i < 2^{32}$
and a known multiplier $m$. Multiplying $Q$ by $m^{-1} \bmod n$ gives $iG$,
which is a point of form (1). `EcCurve.ExtendedBatchDL` uses the multipliers
below, where $\ell$ is the bit length of $n$. The table under
[Supported curves](#supported-curves) gives their number $f$ for each curve.

*   $2^j$ for every multiple $j$ of 8 up to $\ell - 32$. These find a private
    key whose set bits fit in four contiguous bytes that start on a byte
    boundary. This covers form (1). It covers form (2) on every supported curve
    except secp521r1, where $\ell - 32 = 489$ is not a multiple of 8. There the
    highest window covers bits 488 to 519, so a key of form (2) is found when
    bit 520 is 0. When bit 520 is 1, it is found only if
    $(d - 2^{520}) / 2^{488} < T$, with $T$ as below.
*   $1 + 2^{32} + \ldots + 2^{32(w-1)}$ for $w$ from 2 to
    $\lfloor \ell / 32 \rfloor$. These find a 32-bit value repeated in the $w$
    least significant words. This covers form (3).

The search has two steps. Step 1 computes the converted point for every key and
multiplier. Step 2 runs a single baby-step giant-step search over all of those
points. It adds points in batches that share one modular inversion [[BKKLM]],
and it uses a lookup table of the x-coordinates of $iG$ for $0 \le i < T$. For
$k$ keys on the curve, $T$ is about $\sqrt{f \cdot k \cdot 2^{32}}$, or larger
if the curve already holds a larger table (see
[CheckECKeySmallDifference](#checkeckeysmalldifference)). Time and memory are
$O(\sqrt{f \cdot k \cdot 2^{32}})$.

Each x-coordinate in the table stands for both $iG$ and $-iG$, so the search is
a little wider than the forms above: it finds every $i$ with
$-T < i < 2^{32} + T$. The check therefore also flags the negation
$n - i \cdot m$ of a searched value with $0 < i < T$, such as $d = n - 5$, and
values of $i$ slightly above $2^{32}$. Nothing else is searched: the four bytes
must start on a byte boundary, and a repeated value must start at the least
significant word.

A recovered key gets a `DISCRETE_LOG` entry in `test_info.attached_info`, in
hexadecimal. The value is the product $i \cdot m$. It is congruent to the
private key modulo $n$ but not reduced, so for a negated form it is negative:
$d - n$.

The check groups the keys of one call by curve and searches each group in one
batch, which is much faster than checking the keys one at a time. Each key
still gets its own result. Only keys whose point is valid after reducing its
coordinates modulo $p$ are searched, and $k$ above counts only those; see
[CheckValidECKey](#checkvalideckey).

### CheckECKeySmallDifference

Checks whether two keys have private keys that differ by a small amount:
$Q_1 - Q_2 = kG$ with $|k| < 2^{24}$. The check does not compute any private
key. It only finds relations between pairs of keys. Such a relation means the
key generation that produced the keys is badly broken. Whoever learns one of
the two private keys can compute the other as $d_1 = d_2 + k \bmod n$.

The check builds a table of the x-coordinates of $iG$ for $0 \le i < 2^{24}$.
Each x-coordinate stands for both $iG$ and $-iG$. For each key, the check
computes the x-coordinates of its differences to all earlier keys on the same
curve in one batch addition. It looks each one up in the table and confirms
every hit by computing $kG$. Both keys of a matching pair fail. Each gets a
`DISCRETE_LOG_DIFF` entry in `test_info.attached_info` of the form
`key - (x, y) = k * G`, where `(x, y)` is the other key in hexadecimal and `k`
is in decimal. A key close to several others records only one of them. For $N$
keys on one curve the cost is $O(2^{24} + N^2 / 2)$.

The check compares only keys that are passed in the same call and are on the
same curve. Keys checked in separate calls are never compared. A key that is
alone on its curve has nothing to compare against: it passes, and the check
builds no table for that curve. The bound $2^{24}$ is the default of the
`max_diff` constructor argument, and `CheckAllEC` uses that default.

The table lives on the curve object and is shared with the search of
CheckWeakECPrivateKey. It is kept for the rest of the process and rebuilt only
when a check needs a larger one, so later runs on a curve are fast unless they
need a larger table. In the sample output in `examples/ec_public_keys.py`, the
check takes 33.93 s the first time it runs over two secp256r1 keys and 0.00 s
the second time. Lookups use whatever table exists. When CheckWeakECPrivateKey
has already built a table larger than $2^{24}$ on the curve, this check builds
none of its own and also reports differences of $2^{24}$ or more. One call does
that when $f \cdot k > 2^{16}$ for $k$ keys on the curve, for example with 1821
or more keys on a 256-bit curve.

Two identical keys have difference 0 and are skipped as duplicates. A repeated
key therefore fails only if it is also close to some other key. No EC check
reports repeated keys.
